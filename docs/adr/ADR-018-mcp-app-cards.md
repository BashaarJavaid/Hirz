# ADR-018: MCP App cards over the authenticated local tool surface

Date: 2026-09-24. Status: approved implementation plan; verification in progress.

## Decision

Five React cards use the MCP Apps 2.0.0 bridge exclusively. Tools keep their flat
inputs and complete `speakable`; optional discriminated `data.presentation` adds
deterministic display fields, and `data.actions` reuses canonical Actions. No
database migration, new tool, runtime solver, model, or external API call is added.
Existing Pipeline checks, request receipts, exact-version consent, private-case
scope, and phone-only security gates remain authoritative.

Dependencies are pinned as approved: ext-apps/client/core 2.0.0, React/React DOM
19.2.0, their types 19.2.2, Zod 4.2.0, Vite 8.3.0, singlefile 2.3.3 and Playwright
1.57.0. Vite's JSX handling builds five self-contained HTML resources. The
authenticated server refuses incomplete builds; anonymous onboarding retains its
existing startup. A small PEP 517 wrapper delegates to the existing uv backend
after checking distribution assets. A Node 24 Docker stage generates them.

Static templates have no household data, credentials, or configured evidence and
may be read anonymously. Household tools retain their OAuth scopes. Resource
metadata declares empty network and external-resource destinations. Tool metadata
uses `_meta.ui.resourceUri`; `ui/initialize` declares inline, plus customer-operated
fullscreen for plan and scorecard only. Neutral results render the server headline
without specialized controls. Protocol:
[MCP Apps v2.0.0](https://github.com/modelcontextprotocol/ext-apps/blob/v2.0.0/specification/2026-01-26/apps.mdx).

Cards use the 768×480 canvas, published Amazon tokens, light/dark themes, system
sans-serif, 48px controls, visible focus and keyboard controls. Only EV width,
verification opacity and lock position have 200ms ease-out transitions, disabled
under reduced motion. Source badges conservatively distinguish live/simulated;
published rates have a separate label. Source:
[Amazon visual foundations](https://developer.amazon.com/docs/alexaplus/add-ons/mcp-addon-visual-foundations.html).

## Data and authority

Plan consent names the displayed identifier and version. Fullscreen provides
every scheduled action, alternatives, cancellation and a native numeric temporary
car-limit form. Non-security pending actions offer approve/deny. Security requests
explain the unavailable phone path; the card never grants security authority.
Verification offers only one eligible saved contact, about the displayed request;
all terminal states retain the server's wording, and genuine never advises payment.
Door context shares the Pipeline's active-press rule and observation freshness
threshold. Only a twin observation permits the bundled twin snapshot. Requests do
not change the displayed lock state; observations do.

`HIRZ_CARD_EVIDENCE_FILE` explicitly maps household UUIDs to a retained results
file, its SHA-256, rate profile, household variant and wear value. Files are read
at startup; missing or mismatched evidence makes annualized figures unavailable.
Negative estimates remain negative. Backtest extrapolation is distinct from the
selected plan's estimate and is never an assertion about realized savings.

Scorecards select the newest created eligible plan overlapping the audit window,
excluding superseded, abandoned and refreshing plans. An action-specific query
uses that action's plan. The exact horizon is displayed; overlapping estimates
are never summed. Invalid comparisons remain unavailable. Counts are distinct
device actions executed without per-action approval, reaching ASK, reaching DENY,
and receiving VERIFIED read-back, calculated independently of pagination. These
categories can overlap; previews, bookkeeping and private contact cases do not count.

Plan preparation polls every second for at most 30 seconds. Pending verification
polls every two seconds until server expiry; expiry does not invent a terminal
status. Door observations poll every two seconds while visible. Only one call may
be outstanding. Hidden/failed/torn-down cards stop polling. A gesture has one retry
key; retries reuse it, changed intent gets a new key, and replaced-content responses
are ignored. Malformed, unknown or stale data disables affected controls.

## Verification and alternatives

The upstream reference renderer and bridge are pinned to v2.0.0 commit
`352f6ced4d80772e92b4e7a311854481a8d65b04` and kept unchanged. A test-only loopback
relay owns disposable OAuth clients server-side, accepts only the test host origin,
and fixes one household per connection URL. Browser fixtures are generated by
authenticated tools over disposable twin databases; they confer no security authority.
Linux Chromium baselines require author review before item closure.

Rejected: a custom bridge or simulator standing in for reference-host evidence;
production CORS/auth relaxation for the test host; credentials in card JavaScript;
network fonts or CDNs; a component library; hand-entered savings; inferred household
backtest mappings; summing overlapping plan estimates; optimistic lock transitions;
card/voice security approvals; local fabricated verification outcomes; and pulling
Ring, phone approvals or the full simulator forward from their assigned items.

No completion, hosted Alexa latency, real phone delivery, Ring integration, or
security execution is claimed until its own verification gate passes.

## Browser declaration compatibility amendment — 2026-09-24

The author approved keeping all pins and using a separate strict browser-test
TypeScript configuration with `skipLibCheck: true`: Playwright 1.57.0 protocol
declarations use module syntax rejected by TypeScript 6.0.3 (TS1540). Application
type-checking retains declaration checks; browser test source remains strict.
Upgrading Playwright or weakening application checks was rejected. The fourteen
initial Linux Chromium visual baselines were reviewed and approved by the author
on 2026-09-24. [Friction](../friction-log.md#item-27-pinned-playwright-declarations-and-typescript-6--2026-09-24).
